# RPG スキル・レイド計算の整理 計画書

作成: 2026-11-16
見つかった挙動や問題の詳細は [raid-refactor-notes.md](./raid-refactor-notes.md) にある。この計画書は「何を・どの順番で・何をもって完了とするか」をまとめる。

## 目的

スキルを 1 つ足す・直すときに、触る場所を **スキル定義 1 か所** にする。

- **UX**: 計算と表示（確認表示・説明文・戦闘ログ）がずれない。説明文に、その人の今の効果量を出せる。
- **DX**: スキルの追加・調整で、型・集計の式・確認表示・戦闘ログ・説明文を別々に直さなくてよい。書き漏れは型エラーかテストで分かる。
- **AX**: 2,000 行の関数を読まなくても、スキル定義と、その効果を掛ける段階の関数だけ読めば直せる。

## 進め方の決まり

- **段階1は出力を 1 文字も変えない**。挙動の修正（段階2）と混ぜない。
- 1 つの作業ごとに、次を満たしてからコミットする。
  - `npx tsc --noEmit -p .` が通る
  - `npx jest --ci` が通り、**スナップショットが 1 件も変わらない**（段階1の場合）
- 段階1の途中で見つけた奇妙な挙動は、その場で直さずに raid-refactor-notes.md に書き足す。
- 段階2の修正は 1 件ずつ別のコミットにし、スナップショットの差分から「どの構成でダメージがどれだけ変わったか」を集計してコミットの説明に書く。
- 乱数は、ゴールデンテストでは `Math.random` を呼ぶ順番で固定している。段階1では、乱数を引く順番を変えない。

## 段階1（構造だけを変える。出力は同じ）

### 1-1. 覚醒変更の札の補正を 1 つの関数にまとめる

- 朱・青・黄・緑・超覚醒の札でスキル効果を書き換える処理を `applySuperModeTokens(effects, tokens)` にする。
- 呼び出し元: raid.ts（`getTotalDmg`）、rpg/index.ts（2 か所）、skills.ts（`getTotalEffectString`）。
- メッセージの追加や覚醒回数の加算は呼び出し側に残す。
- **完了条件**: 4 か所がこの関数を呼んでいて、補正の式がほかに残っていない。

### 1-2. 鳩車（コンテスト型）の計算を 1 つの関数にまとめる

- 先に「RPG スキル バフ 鳩車」の出力を、構成ごとのスナップショットで固定する。
- `computeContestDex(effects, data)` を作り、器用さ・仕上げの手順（見出しと倍率）の一覧と最終値を返す。
  - 見出しは今は戦闘ログと確認表示で言葉が違うので、手順に両方の見出しを持たせる。
- `getTotalDmg3` と `getHatogurumaEffectString` はこの一覧を整形するだけにする。
- **完了条件**: 器用さ・仕上げの式が 1 か所にしかない。

### 1-3. 戦闘ログの書き方をまとめる

- `buff += 1` と `if (buff > 0) message += "\n"` の組み合わせ（raid.ts で約 120 か所）を、ログ用の小さなクラスにまとめる。
  - `log.buff(text)`（バフの行を足す）、`log.verbose(text)`（詳細ログのときだけ足す）、`log.endSection()`（バフが 1 行でもあれば改行）
- **完了条件**: `getTotalDmg` の中に `buff` の数え方を手で書いた箇所が残っていない。

### 1-4. getTotalDmg の状態をまとめて、段階ごとの関数に分ける

- ローカル変数（攻撃力・防御・速度・体力・アイテム・各種スタックなど）を `RaidBattleState` にまとめる。
- 次の関数に分ける（名前は仮）。
  1. `prepareRaidBattle` — データ読み込み・お守り付与・覚醒判定・投稿数・ステータス計算
  2. `applyPreBattleModifiers` — 調子補正・天国か地獄か・風・遂・土・非戦闘時補正・防御貫通など、ループ前の補正
  3. `runRaidTurn` — 1 ターン分（ターン開始時の補正・アイテム・敵の先制攻撃・自分の攻撃・敵の攻撃）
  4. `finishRaidBattle` — 勝利判定・戦士マーク・結果の文章・返り値
- 字下げがずれているところ（`let maxdmg` など）もここで直す。
- **完了条件**: `getTotalDmg` 本体が、これらを順番に呼ぶだけになる。どの関数も数百行以内。

### 1-5. 条件付きの倍率をスキル定義（データ）にする

- 「条件を満たしたらパワー・防御に倍率を掛ける」だけの効果を、次の形の定義にする。

  ```ts
  { effect: "dart", label: "土スキル効果", phase: "preBattle", when: "noDamageCap", stats: { atk: (v) => 1 + v * 0.5 } }
  ```

  - `phase`: 掛ける時点（`preBattle` / `turnStart` / …）。1-4 で分けた段階に対応する。
  - `when`: 発動条件。自由な関数ではなく、決まった名前（`always` / `battle` / `nonBattle` / `noDamageCap` / …）から選ぶ。確認表示が「パワー」「戦闘時パワー」「非戦闘時パワー」のどの行に入れるかを判断できるようにするため。
  - 例外的な書式の詳細ログは、定義に書式の上書きを書けるようにする。
- この定義から、戦闘の計算・詳細ログ・確認表示（effect-display.ts の `stats`）を作る。
- 状態を持つものや、ほかの処理に割り込むもの（継戦融合武装・怠惰・超越など）は、従来どおり処理を書く「フック」として残す（ログは 1-3 の関数を使う）。
- 定義の並び順は今の処理の順番に合わせる（ログの順番を変えないため）。
- **完了条件**: 移した効果の倍率の式が、定義の 1 か所にしかない。

### 1-6. ステータス上昇のグループをスキル定義に持たせる

- 番号付きのキー（atkUp〜atkUp6、defUp〜defUp5、atkDmgUp2、defDmgUp2）をやめ、スキル定義に `stats`（atk・def・atkDmg・defDmg）と `statGroup` を持たせる。
  - 同じグループの中は足し算、違うグループどうしは掛け算。`statGroup` を省略したらスキル名がグループになる。
  - 1 個ごとに ×1.04 になる `atkUpBonus` は、規則を名前で表す（例: `compound`）。
- 合成お守りは、効果をキーで 1 つにまとめるのではなく、元のスキルのグループごとに足す。
- 集計結果の `atkUp` などの形は変えない（戦闘側の参照は触らない）。
- 段階1では、今の足し算を保つため、伝説と連続・毎日ボーナス強化に同じ `statGroup` を明示する。
- 削除済みのスキルなど、保存データに残っている古いキー（`atkUp2` など）を読み込めるように変換を残す。
- スキル効果X倍（下の「スキル効果X倍への対応」）は、グループにまとめる **前に** スキルごとに掛ける。
- **完了条件**: `SkillEffect` 型から番号付きのキーがなくなる。新しいスキルが独立した倍率を持つのに、キーの追加がいらない。

### スキル効果X倍への対応（1-6〜1-8 に共通）

対象は、スキル効果がX倍になるレイドボス（今は `:mk_giga:` の 3 倍）と、「RPG スキル バフ 3」の確認表示。今の `aggregateSkillsEffects` の動き:

1. スキルごとに、ユニークスキル（`unique` / `amuletUnique`）は効果を 1 倍のまま残し、代わりに補填として 1 個ごとに `uniqueX *= 1 + 0.06 × (X − 1)` を掛ける（3 倍なら 1 個につき ×1.12）。補填は最後にパワー・防御の倍率へ掛ける。
2. それ以外のスキルは、効果のすべての値を X 倍する（真偽の代わりに 1 を入れている効果も X になる）。
3. そのあとで、同じキーを足す → グループの掛け算 → 曜日ボーナスなどの補正（遂の上限・虹の変換など、しきい値を持つ補正を含む）の順に進む。

計画への反映:

- **スキルごとの倍率の規則を、スキル定義で表す**。「X 倍にする」「1 倍のまま補填を入れる」を `unique` から決めるのではなく、規則として名前で持たせる（既定は今と同じく `unique` / `amuletUnique` から決める）。
- **補填はグループとして表す**。ユニークスキル 1 個ごとに、独立したグループ（パワー・防御 +0.06 × (X − 1)）を足すのと同じ計算になる。1-6 の「違うグループどうしは掛け算」にそのまま乗る。
- **順番を守る**。X 倍 → グループごとの足し算 → グループの掛け算 → 補正、の順は変えない。1-7 の補正の表は、しきい値（遂の効果量が 1 を超えたらパワーに変換するなど）が X 倍のあとの値で判定されるので、**順番付きの配列** にする。
- **合成お守り**: 今は効果を 1 つにまとめた時点で、元のスキルが `amuletUnique` だったという情報がなくなる。そのため、罪スキル（傲慢・強欲・憤怒・暴食・怠惰・嫉妬の力）のお守りは、X 倍のボスで 1 倍のままにならず **3 倍になっている**（`amuletUnique` の判定は、実質どこでも効いていない）。1-6 で合成お守りが元のスキルの情報を持つようになっても、段階1では今の動き（お守りの効果はすべて X 倍）を保つ。
- **説明文（1-8）**: `ctx` に X を入れ、「今の効果量」の表示で、X 倍のボスでの値や、ユニークスキルの「1 倍のまま・代わりにステータス +12%」を出せるようにする（使い始めるのは段階2）。
- **安全網**: ゴールデンテストの全ボスに `:mk_giga:`（3 倍）が含まれ、構成に罪スキルのお守り・ユニークスキル（分散型・食いしんぼう・攻めの守勢など）が入っている。確認表示は `effect-display.spec.ts` の「スキル効果3倍」8 件。1-6 の前に、伝説・気性が荒い・かるわざなど番号付きのグループを使うユニークスキルを含む構成を、3 倍のケースに足す。

### 1-7. 効果量の補正を表にする

- 集計関数（`aggregateSkillsEffects`）の中に if 文で並んでいる補正（曜日ボーナス ×5/3、水による氷・雷の強化、虹、初心者、分散型、遂の上限など）を、効果の種類ごとの表にする。
- 集計も説明文（1-8）もこの表を使う。
- **完了条件**: 補正の式が表の 1 か所にしかない。

### 1-8. スキル説明文を、効果量を受け取る関数にする

- 先に全スキルの desc・info をスナップショットで固定する。
- `info` を「文字列または関数」で書けるようにし、関数版は `(v: SkillEffect, ctx) => string` とする。
  - 基本の効果量で表示した結果が、今の文字列と完全に一致することをテストで確かめながら、少しずつ移す（数値を直書きしているのは 78 スキル中 66）。
  - 一致しないものは、説明文と実際の効果がずれているので、段階2の候補として記録する。
- `describeSkill(skill, data, mode)` を作り、「詳細表示の札があれば info、なければ desc」の選び方（スキル一覧・変更・選択・複製・お守りの店・カスタムお守りの店など）をすべてこれに置き換える。
  - `mode`: 基本の効果量（店・変更候補）／今の効果量（自分のスキル一覧。1-7 の補正込み）
- 段階1では「今の効果量」の表示は使わない（出力が変わるため）。使い始めるのは段階2。
- **完了条件**: info に数値を直書きしているスキルがなくなる。説明文の選び方が 1 か所にまとまる。

### 段階1の順番と依存関係

- 1-1・1-2 は独立していて、すぐ始められる。
- 1-3 → 1-4 → 1-5 の順（1-5 は分けた段階とログ関数を使う）。
- 1-6 → 1-7 → 1-8 の順（1-8 の「今の効果量」は 1-7 の表を使う）。
- 1-3〜1-5（raid.ts）と 1-6〜1-8（skill-data.ts・skills.ts）は触るファイルがほぼ分かれているので、並行して進められる。

## 段階2（挙動を直す。1 件ずつ別コミット）

候補（詳細は raid-refactor-notes.md）:

- 土属性の代わりの効果の発動条件（戦闘中でも出る）と、説明文の「非戦闘時」の食い違い
- 朱覚醒の詳細ログが別の値（`atkDmgUp`）を表示している
- 1 ターン目のアイテム最低効果が `NaN` で効かない

- 罪スキルのお守りが、スキル効果X倍のボスで 1 倍のままにならず X 倍になっている（`amuletUnique` の判定が効いていない）。意図どおりにするか決める

各修正は利用者から見るとバランス調整になる。告知が必要かどうかは、コミットに書いた増減を見て判断する。管理者の再計算コマンド（`recalculateRaidResult`）は今の計算式で再計算するので、修正後に過去のレイドを再計算すると修正分も反映される。

## 段階3（通常戦闘・木人に広げる）

- 通常戦闘（rpg/index.ts の `handleNormalCommands` の中）と木人にゴールデンテストを足す。
- 1-5 の倍率の定義と 1-3 のログ関数を通常戦闘でも使い、レイドとの重複（天国か地獄か・土・炎・敵ステータスボーナスなど）をなくす。
- レイドと通常戦闘で、土とアイテムの掛かる順番が違う件は、ここで揃えるかどうか決める。

## 気をつけること

- **保存データ**: プレイヤーのスキルはオブジェクトごと保存されている。集計は名前で今の定義を探すが、削除済みのスキルは保存された古い効果がそのまま使われる。キーや形を変えるときは、古い形を読める変換を残す。
- **乱数の順番**: 段階1で処理を動かすときは、乱数を引く順番を変えない（ゴールデンテストで検出できる）。
- **getTotalDmg2・getTotalDmg3**: 1-4 で共通部分（準備・返り値）が見えてきたら、合わせて整理する。
